**Evidence.** Rows marked *(run)* were observed by calling the starter's helper function and the current one directly with the input shown. Every other row comes from comparing the starter source with the current source; no test result is claimed for it. Locations are function names (no line numbers).

## Looked at and kept (not defects)

- **Calendar dates as `YYYY-MM-DD` strings with `$gte`/`$lte`.** DATA_MODEL.md says dates are plain strings on purpose; string order is chronological, so `attendance_list_filter` keeps the string comparison.
- **New punch-in record defaults** (`punch_out` null, `work_hours` null, `overtime_minutes` 0, `half_day` false, `history` []) match the DATA_MODEL table; `build_attendance_doc` keeps them.
- **Status codes and messages** the starter already used (201 on create, 409 "already punched in for this date", the `items / total / page / page_size` envelope) match openapi.yaml and were kept.

## Analytics: behaviour that depends on interpretation

The contract does not settle these, so they are documented decisions, not claimed facts: records dated before an employee's `joined_on` still count in the analytics; an empty-string department is left out of the department summary; the trend allows at most 92 inclusive dates; the 7-day moving average averages the already-rounded daily rates.
## Phase 6: audit results, what was run

- **Fixed and tested (`tests/test_phase6.py`, in-memory fakes, no MongoDB):**
  - A PyMongo error that no route handles is now returned as `503 {"detail": "database unavailable"}` (one handler; driver message not returned, only the exception class name logged). Before, such an outage produced a plain-text 500. `DuplicateKeyError` -> 409, validation 422 and 404 are unchanged; programming errors stay 500.
  - `POST /attendance/punch-out` with `punched_at` before the employee's open punch-in returned 404; the contract says 422 (`punched_at <= punch_in`). It now returns 422. Equal to the punch-in and more than 24 hours were already 422, exactly 24 hours is allowed, a closed record is 409. The atomic conditional close is unchanged; the extra read runs only when no record starts at or before `punched_at`.
- **Inspected, not changed:** startup and `/health` readiness, index definitions, the concurrency mechanisms (unique indexes plus `DuplicateKeyError`; conditional `find_one_and_update`).
- **MongoDB configuration (inspected, behaviour kept, tested):** the assignment requires reading `MONGO_URI` / `MONGO_DB` from the environment with real variables taking priority over `.env`, and no hard-coded connection details. It neither makes `MONGO_URI` mandatory nor explicitly allows a localhost default, so an unset `MONGO_URI` still uses PyMongo's own default host. Making it mandatory is a possible stricter reading; it was not applied because the contract does not require it.
- **Boundary interpretation:** when no record is eligible because every punch-in is later than `punched_at`, the nearest later record is checked and the request returns 422, whether that later record is open or closed. If an older record is eligible and is already closed, the most-recent-eligible-record rule still yields 409.
- **Earlier results, reported by the author and not re-run in this review:** a full regression of 608 tests passing with 1 skipped, and explain diagnostics on MongoDB 7.0.43 for six trend scenarios (about 100,000 attendance records, 5,000 employees) reporting IXSCAN without COLLSCAN. They do not establish that every analytics endpoint or query shape was tested at that scale.
